# Simurgh dogfood — 2026-07-13

**What this proves:** two independent agents can concurrently acquire isolated
iOS Simulator leases, build the same Xcode scheme against their own isolated
`DerivedData`, install, launch, and screenshot their own booted clone, and
release — with zero collisions and zero manual UDID handling. This is the M3
milestone's exit demo per `docs/ROADMAP.md`.

## Mechanics — an honest note on what was actually run

The roadmap's M3.3 line describes "TWO parallel Claude Code sessions" each
registering `simurgh mcp` and driving it as a real MCP client. Within this
single orchestrating Claude Code session, a dispatched subagent cannot attach
to a new MCP server that isn't already part of the session's own `.mcp.json`
(MCP servers connect at session startup, not dynamically mid-session) — so a
literal "two fresh Claude Code sessions each holding their own live MCP
connection to `simurgh mcp`" was not achievable from inside this orchestrator
run.

What was actually run instead: **two parallel `Agent`-tool subagents, each
independently driving `simurgh` through its CLI** (`simurgh acquire` /
`simurgh exec` / `simurgh release`), against the same running daemon. This
exercises the *identical* underlying `internal/broker`/`internal/provisioner`/
`internal/isolator` concurrency and isolation machinery the MCP tools also
wrap — the CLI and the MCP server are both thin clients over the exact same
`internal/daemon` RPCs (confirmed in M1.5b and M3.1). The one thing this
substitution does *not* directly exercise is the MCP wire protocol itself
under concurrent load — but M3.1's own live acceptance test already
independently proved a real MCP client (the official SDK's `CommandTransport`)
round-trips correctly against this daemon, so that gap is covered separately,
just not in the same run. A fully faithful "two real Claude Code windows each
pointed at a project with `simurgh init` already run" is one owner-run manual
step away from full fidelity, and is a reasonable thing to ask the owner to
spot-check once, rather than something this orchestrator could fabricate
evidence for.

## A real bug was found and fixed during this exercise

The first attempt at this dogfood run failed both agents. Root cause,
confirmed by direct code inspection and live reproduction: `internal/
watcher.decide()` checked owner-PID liveness **unconditionally**, regardless
of `ReleaseOnPIDExit` — and the CLI's `acquire` command records its own
one-shot process's PID (`os.Getpid()`) as the lease owner, which exits the
instant `acquire` returns. Combined, every plain `simurgh acquire` (no
`--rm`) had its lease reclaimed — and its device **deleted** — within one
watcher tick (5s), regardless of a multi-minute TTL. One agent's fast build
(12.8s) won the race against reclamation; the other's didn't and hit
`xcodebuild: error: Unable to find a device matching the provided destination
specifier`.

Fixed in `internal/watcher/watcher.go`: owner-PID liveness is now checked
**only** when `ReleaseOnPIDExit` (`--rm`) is `true`, matching what that flag
was always documented to mean. Live-verified the fix directly (a lease
without `--rm` survived 15+ seconds/3 watcher ticks past its acquiring
process exiting; a lease with `--rm` was still correctly reclaimed after its
owner died) before re-running this dogfood. Full details:
`docs/plans/orchestrator-state.md`'s 2026-07-13 evidence log and the merge
commit `66ae3f6`.

This is exactly the kind of thing dogfooding exists to catch — a bug that
every prior package's live `[mac]` test (which always ran short, `--wait`-
then-immediately-release flows) never had a chance to hit, because it never
held a lease across a slower multi-step workflow the way a real agent
actually would.

## Run 2 (with the fix) — full results

Fresh daemon, fresh `SIMURGH_HOME`, real `simctl` throughout. Two `Agent`-
tool subagents dispatched in parallel, each told to independently
acquire → verify-active → build → install → launch → screenshot → release,
with no coordination between them.

| | Agent A | Agent B |
|---|---|---|
| Lease ID | `lease-1` | `lease-2` |
| Device UDID | `075CB5DC-A245-49FB-B35B-4F51BAC8D345` | `659D4EC5-A03D-49B1-8001-0908CE96F746` |
| Label | `agent=A` | `agent=B` |
| Acquired at | 05:14:24.885 | 05:14:39.982 |
| Build result | `** BUILD SUCCEEDED ** [45.228 sec]` | `** BUILD SUCCEEDED ** [49.759 sec]` |
| Install/launch | both exit 0 (`dev.simurgh.fixtures.sampleapp: 24546`) | both exit 0 (`dev.simurgh.fixtures.sampleapp: 25398`) |
| Screenshot | `2026-07-13-agent-a-screenshot.png`, 145,150 bytes, 1206×2622 PNG | `2026-07-13-agent-b-screenshot.png`, 151,504 bytes, 1206×2622 PNG |
| Release | `state: "released"` | `state: "released"` |
| Post-release device check | clone gone from `simctl list devices` | clone gone from `simctl list devices` |

**Concurrency proof:** lease-1's window was 05:14:24 → (build finished
~05:15:10) and lease-2's was 05:14:39 → (build finished ~05:15:30) — both
leases were genuinely ACTIVE simultaneously from 05:14:39 to at least
05:15:10, a real overlapping window, not a sequential run. Agent B
independently confirmed this live from inside its own run: *"Agent A's
lease-1 was concurrently active and isolated, as expected"* (checked via its
own `xcrun simctl list devices` call during step 2, which showed both
`simurgh-clone[lease-1:...]` and `simurgh-clone[lease-2:...]` booted at
once).

**Isolation proof:** each lease got its own `DerivedData`/`ModuleCache`/
`SwiftPM` directory under `$SIMURGH_HOME/leases/<id>/` (confirmed in each
release JSON's `env` block) and its own simulator clone (`cloneOf` both
point at the same shutdown base, `D01C2165-...`, but the two clone UDIDs are
distinct) — matching M2.1's own concurrent-build isolation proof, now
demonstrated end-to-end through install/launch/screenshot as well, not just
`xcodebuild build`.

**Zero manual UDID handling:** both agents used exactly the UDID returned by
their own `acquire` call — neither ever ran `xcrun simctl list devices` to
*pick* a device, only to *verify* the one they were given (an intentional,
correct verification step, not device selection).

**Cleanup:** final `xcrun simctl list devices | grep -i simurgh` after both
releases showed only the pre-existing `simurgh-base[iPhone 17 Pro:27.0]`,
untouched throughout both runs (the failed first attempt and the successful
second one). `~/.simurgh` was never touched — the whole exercise ran against
an isolated scratch `$SIMURGH_HOME`.
