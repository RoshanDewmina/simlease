# M3.2 work package — `simurgh init`

## Goal

Implement `simurgh init`: writes `.simurgh.yaml` (default device spec +
labels for the current project), an agent-facing rules snippet, and
registers `simurgh mcp` in `.mcp.json`. Idempotent — safe to run more than
once without duplicating entries or clobbering user edits.

## Source requirements

- `docs/ARCHITECTURE.md:223-236` (§9 CLI surface): `simurgh init  # project
  setup: .simurgh.yaml + agent snippet + .mcp.json entry`.
- **Confirmed real `.mcp.json` schema** (read directly from a working
  example on this machine, do not guess a different shape):
  ```json
  {
    "mcpServers": {
      "<name>": {
        "type": "stdio",
        "command": "<binary>",
        "args": ["<arg>", ...],
        "env": {}
      }
    }
  }
  ```
  For `simurgh`, the entry should be:
  ```json
  "simurgh": {
    "type": "stdio",
    "command": "simurgh",
    "args": ["mcp"],
    "env": {}
  }
  ```
  (assumes `simurgh` is on `$PATH` — this matches how every other stdio
  entry in a real `.mcp.json` on this machine is expressed, e.g. `xcrun
  mcpbridge` — do not hardcode an absolute path to the current binary,
  that would break the moment the binary moves).
- `internal/broker.DeviceSpec`/M1's existing types (existing, read-only) —
  `.simurgh.yaml`'s default spec fields should mirror `DeviceSpec`'s
  shape (`platform`, `model`, `runtime`) plus a `labels` map, so a future
  package reading this config (config-file reading is still out of scope
  product-wide per M1.1/M1.2's existing scope notes — this package only
  WRITES the file, nothing reads it yet) has an obvious, consistent shape
  to parse later.
- This project's own `AGENTS.md`/`CLAUDE.md` files (read them) as the
  reference shape for what an "agent rules snippet" looks like in this
  ecosystem — the snippet `simurgh init` writes should be a short,
  pointed block (not a whole file) that a project's own `AGENTS.md`/
  `CLAUDE.md` could `@`-import or paste in, stating the same discipline
  the M3.1 tool descriptions already establish: use the MCP tools, never
  pick a UDID from `simctl` yourself, release when done.

## Exact write-set

- `internal/cli/init.go` (new) — testable logic (the existing
  `internal/cli` package already holds `doctor.go`'s `Check`/`RunChecks`
  pattern from M0.4/M2.3 — follow its style, this file is a sibling, not
  a rewrite of that pattern):
  - `func WriteSimurghYAML(path string, force bool) (written bool, err
    error)`: writes a minimal default `.simurgh.yaml` (e.g. `spec:
    {platform: iOS, model: "iPhone 17 Pro", runtime: ""}` and an empty
    `labels: {}`) ONLY if the file doesn't already exist, unless `force`
    is set — idempotent by default, never silently overwrites a user's
    existing customized file. Returns whether it actually wrote anything
    (for the CLI to report "created" vs "already exists, skipped").
  - `func AgentRulesSnippet() string`: returns the short, static
    agent-guidance text block (pure function, easy to unit-test its
    content directly, e.g. assert it mentions "lease_acquire" and "never
    pick a UDID").
  - `func UpsertMCPEntry(path string, name string, entry MCPServerEntry)
    (changed bool, err error)` where `MCPServerEntry{Type, Command string;
    Args []string; Env map[string]string}` (matching the confirmed schema
    above exactly, JSON tags `type`/`command`/`args`/`env`): reads the
    existing `.mcp.json` if present (preserving every other server entry
    untouched — this file commonly has multiple servers already
    configured, per the real example above; do not clobber unrelated
    entries), parses its top-level `mcpServers` object, upserts exactly
    the `name` key with `entry` (idempotent: calling this twice with the
    same `entry` results in `changed=false` the second time — compare
    before writing), writes back preserving readable JSON formatting
    (indented). If the file doesn't exist, create it with just the one
    `simurgh` entry under `mcpServers`. If the file exists but is
    malformed JSON, return a clear error rather than silently
    overwriting it (never destroy a file this package didn't create just
    because it couldn't parse it).
- `internal/cli/init_test.go` — `WriteSimurghYAML`: creates on first call,
  skips (no overwrite) on second call without `force`, overwrites with
  `force`; `UpsertMCPEntry`: creates a fresh file correctly; on an
  existing file with OTHER unrelated server entries, adds `simurgh`
  without touching the others (assert byte-for-byte the other entries are
  unchanged); calling twice with identical input is a no-op the second
  time (`changed=false`); malformed existing JSON returns an error, does
  not overwrite.
- `cmd/simurgh/init.go` (new) — `simurgh init [--force] [--json]`: calls
  the three functions above against `./.simurgh.yaml` and `./.mcp.json`
  (project-relative, i.e. the current working directory — this command
  is meant to be run from inside a project repo, not against
  `~/.simurgh`), prints the agent rules snippet to stdout (so a user can
  redirect/paste it — e.g. `simurgh init >> AGENTS.md` should read
  reasonably, though the primary output is status lines, not just the
  raw snippet dumped with no context — use your judgment on exact
  formatting, prioritize a human running this interactively for the
  first time being able to tell what happened). Reports what was
  created vs. already-existed vs. skipped. Exit 0 on success (including
  "nothing to do, already initialized"), non-zero only on a real error
  (e.g. malformed existing `.mcp.json`).
- `cmd/simurgh/main.go` — wire `init`.

Do not edit `internal/store`, `internal/broker`, `internal/provisioner`,
`internal/watcher`, `internal/reaper`, `internal/safety`, `internal/
isolator`, `internal/daemon`, `internal/ipc`, `internal/mcp`, CI config, or
any doc other than `docs/plans/orchestrator-state.md`.

## Explicitly out of scope

- Reading `.simurgh.yaml` anywhere else in the codebase — this package
  only writes it. Wiring `broker`/`provisioner` to actually read config
  defaults from it is a future package, not this one.
- Any prompt/interactive flow — `simurgh init` is a single non-interactive
  command.
- Detecting/validating that `simurgh` is actually on `$PATH` before
  writing the `.mcp.json` entry — write the entry as documented; if the
  binary isn't on PATH that's a separate, pre-existing user environment
  concern, not this command's job to fix.
