# M4.2 work package — daemon log rotation + `simurgh daemon status`

## Goal

Make the daemon's own logging actually reach a real, rotating file at
`DefaultLogPath()` (`~/.simurgh/logs/simurghd.log`, already resolved by an
existing helper from M0.2b but never used for the daemon's own output —
today `log.Printf` goes to bare stderr, and `ReclaimLoop`'s `Logger` field
defaults to `log.Printf` too). Add `simurgh daemon status [--logs]`
(currently only `daemon run` exists — `status`/`stop`/`install` were
explicitly deferred starting at M0.2b).

## Source requirements

- `docs/ROADMAP.md`'s M4 bullet: "Log rotation, `daemon status --logs`."
- `docs/ARCHITECTURE.md:223-236` (§9 CLI surface): `simurgh daemon
  run|status|stop|install`. This package builds `status` only — `stop`
  and `install` (LaunchAgent) remain out of scope (matching M0.2b's
  original deferral; `daemon run &` stays the accepted dev-path per the
  M0 GATE's own "or install" wording).
- `docs/ARCHITECTURE.md:253` (§10): "Logging: structured (slog), rotating
  file + `simurgh daemon status --logs`." — use `log/slog` (Go stdlib,
  already available, no new dependency) for structured logging, not bare
  `fmt`/`log.Printf` formatting, going forward for daemon-originated log
  lines.
- `cmd/simurgh/daemon.go`'s existing `DefaultLogPath()` — reuse this
  exact path convention (honors `$SIMURGH_HOME`), do not invent a new one.

## Design — no new dependency for rotation

This project has consistently preferred small hand-rolled implementations
over new dependencies for well-understood, bounded problems (`internal/
store`'s atomic-write, every package's local error-triple duplication
instead of a shared errors package). Log rotation is the same kind of
problem — implement a small size-based rotating `io.Writer`, not a new
`go.mod` dependency:

- `internal/logrotate/logrotate.go` (new package): `type Writer struct {
  path string; maxBytes int64; maxBackups int }`, a `func New(path
  string, maxBytes int64, maxBackups int) (*Writer, error)` that opens/
  creates `path` (mode 0600, parent dir 0700 — matching every other
  file-permission convention in this codebase), and a `Write([]byte)
  (int, error)` method satisfying `io.Writer`: before each write, if the
  current file size + the incoming write would exceed `maxBytes`, rotate
  (rename `path` → `path.1`, `path.1` → `path.2` ... up to `maxBackups`,
  drop the oldest, open a fresh `path`) — mutex-guarded for concurrent
  writers (the daemon's various goroutines — `ReclaimLoop`, request
  handlers — may log concurrently). Sensible default: `maxBytes` = 10MB,
  `maxBackups` = 3 (documented constants, not hardcoded magic numbers).
- `internal/logrotate/logrotate_test.go` — writes exceeding `maxBytes`
  trigger a real rotation on a `t.TempDir()` path (not fakes — this is
  cheap, deterministic, real-filesystem-testable); confirm old backups
  beyond `maxBackups` are actually removed, not just renamed indefinitely;
  concurrent writes from multiple goroutines don't corrupt/interleave
  (race-detector-clean).

## Exact write-set

- `internal/logrotate/logrotate.go`, `internal/logrotate/logrotate_test.go`
  — as designed above.
- `cmd/simurgh/daemon.go`: `runDaemon()` constructs a
  `logrotate.New(logPath, ...)` writer at `DefaultLogPath()` and sets it
  as the destination for a `slog.Logger` (`slog.New(slog.NewTextHandler
  (writer, nil))` or similar — keep it simple, structured key=value text
  is fine, JSON is not required). Thread this logger into
  `broker.BrokerOptions.Logger` and `daemon.ReclaimLoop.Logger` (both
  already accept a `func(format string, args ...any)`-shaped seam — wrap
  the `slog.Logger` in a small adapter function matching that signature,
  or check whether it's cleaner to widen those seams to accept `*slog.
  Logger` directly; if you widen the seam type, that touches `internal/
  broker` and `internal/daemon` — a small, mechanical, behavior-preserving
  signature change is acceptable here since M4 is explicitly the
  hardening/polish milestone, but do not change what either seam log
  when, only how the message gets written).
- `cmd/simurgh/daemon.go` (continued): a new `runDaemonStatus(logsFlag
  bool, jsonFlag bool) int` implementing `simurgh daemon status [--logs]
  [--json]`: dials the socket with a short timeout WITHOUT auto-starting
  (same non-auto-starting direct-dial pattern `internal/cli/doctor.go`'s
  `dialPing`-equivalent already uses — do not use `ipc.Dial`, which
  auto-starts) and reports reachable/unreachable; with `--logs`, reads
  and prints the last ~50 lines of `DefaultLogPath()` (tail-style — a
  simple "read whole file if small, else seek from the end" is fine for
  v0, no need for a sophisticated streaming tail). Exit 0 if the daemon
  is reachable (regardless of whether `--logs` found a log file — a
  missing/empty log file is not an error, just report "no logs yet"),
  exit 4 (environment problem, matching `doctor`'s convention) if
  unreachable.
- `cmd/simurgh/main.go`: wire `daemon status` as a `daemon` subcommand
  (alongside the existing `daemon run`).

Do not edit `internal/store`, `internal/provisioner`, `internal/watcher`,
`internal/reaper`, `internal/safety`, `internal/isolator`, `internal/ipc`,
`internal/cli`, `internal/mcp`, `internal/pressure`, CI config, or any doc
other than `docs/plans/orchestrator-state.md`. The permitted edits outside
the new `internal/logrotate` package are exactly: `cmd/simurgh/daemon.go`,
`cmd/simurgh/main.go`, and — only if you determine widening the logger
seam type is the cleaner path — the minimal signature changes in
`internal/broker` (the `Logger` field type) and `internal/daemon` (the
`ReclaimLoop.Logger` field type). If you touch either of those, keep the
diff to the type/field declaration and call sites only — no behavioral
changes to what gets logged or when.

## Explicitly out of scope

- `simurgh daemon stop`/`daemon install` (LaunchAgent) — still deferred,
  note this explicitly in your report rather than silently skipping.
- Log level filtering/verbosity flags — always log at one level for v0.
- Structured JSON logging — `slog`'s text handler is sufficient; JSON
  output is not required by this spec.
